1. Purpose

This document defines the core information that CredentialFlow may need to manage during the MVP.

The data model is designed to support the worker workflow, management workflow, credential tracking, verification, reminders, extension requests and audit history.

The MVP should collect only information necessary for the intended workflow.

⸻

2. Core Data Objects

The initial CredentialFlow data model consists of:

1. Worker
2. Organisation
3. Credential
4. Credential Type
5. Verification Record
6. Reminder
7. Extension Request
8. Audit Event

⸻

3. Worker

A Worker represents an authorised person using CredentialFlow.

Example fields

Field	Purpose
Worker ID	Unique internal identifier
Name	Worker identification
Email	Account and notification purposes
Organisation ID	Links worker to organisation
Role	Workforce role where required
Account Status	Active / inactive
Created Date	Account creation
Updated Date	Last update

CredentialFlow should avoid collecting unnecessary personal information.

⸻

4. Organisation

An Organisation represents the workforce organisation using CredentialFlow.

Example fields

Field	Purpose
Organisation ID	Unique identifier
Organisation Name	Organisation identification
Organisation Status	Active / inactive
Configuration	Organisation-specific settings
Created Date	Account creation
Updated Date	Last update

⸻

5. Credential Type

A Credential Type defines what type of credential is required.

Examples may include:

* Qualification
* Licence
* Clearance
* Certificate
* Training credential
* Organisation-specific credential

Example fields

Field	Purpose
Credential Type ID	Unique identifier
Name	Credential name
Description	Explanation of requirement
Renewal Period	Applicable renewal period
Verification Required	Yes / no
Active	Whether currently used

⸻

6. Credential

A Credential represents an individual worker’s credential record.

Example fields

Field	Purpose
Credential ID	Unique identifier
Worker ID	Associated worker
Credential Type ID	Type of credential
Document Reference	Uploaded document reference
Credential Number	Reference number where applicable
Issue Date	Date issued
Expiry Date	Date of expiry
Issuing Organisation	Issuer where applicable
Status	Current workflow status
Verification Status	Verification state
Created Date	Record creation
Updated Date	Last update

⸻

7. Credential Status

CredentialFlow should maintain a clear status.

Possible values include:

* MISSING
* SUBMITTED
* VERIFICATION_PENDING
* VERIFIED
* EXPIRING_SOON
* EXPIRED
* EXTENSION_REQUESTED
* EXTENSION_APPROVED
* EXTENSION_DECLINED

The exact status model may be refined during technical development.

⸻

8. Verification Record

A Verification Record stores information about an applicable verification process.

Example fields

Field	Purpose
Verification ID	Unique identifier
Credential ID	Associated credential
Verification Method	How verification occurred
Verification Status	Pending / verified / unable to verify
Verification Date	Date processed
Verified By	Authorised person/system
Notes	Relevant information

CredentialFlow must distinguish between:

Document submitted

and

Credential verified

A submitted document must not automatically be represented as verified.

⸻

9. Reminder

A Reminder represents a notification generated by the credential workflow.

Example fields

Field	Purpose
Reminder ID	Unique identifier
Credential ID	Associated credential
Worker ID	Recipient
Reminder Type	Expiry / overdue / action required
Scheduled Date	Intended notification date
Sent Date	Actual notification date
Status	Scheduled / sent / failed

Reminder timing should be configurable.

⸻

10. Extension Request

An Extension Request represents a worker request for additional time where organisational policy permits.

Example fields

Field	Purpose
Request ID	Unique identifier
Credential ID	Associated credential
Worker ID	Requesting worker
Explanation	Reason for request
Expected Document Date	Expected submission date
Request Date	Date submitted
Status	Pending / approved / declined
Decision Date	Date decided
Decision Maker	Authorised decision-maker
Decision Notes	Relevant management notes

⸻

11. Audit Event

An Audit Event records important actions within CredentialFlow.

Example fields

Field	Purpose
Event ID	Unique identifier
Event Type	Action performed
User ID	Person/system performing action
Credential ID	Related credential where applicable
Timestamp	Date and time
Result	Outcome
Metadata	Additional permitted information

Examples:

* Credential uploaded
* Credential submitted
* Verification initiated
* Verification completed
* Reminder sent
* Explanation submitted
* Extension requested
* Extension approved
* Extension declined
* Credential status changed

⸻

12. Relationships

The core relationships are:

ORGANISATION
      │
      └── WORKERS
             │
             └── CREDENTIALS
                    │
                    ├── VERIFICATION RECORDS
                    │
                    ├── REMINDERS
                    │
                    ├── EXTENSION REQUESTS
                    │
                    └── AUDIT EVENTS

Credential Types define the requirements associated with individual credentials.

14. Data Minimisation

CredentialFlow should follow a data-minimisation principle.

Only information required to operate the intended workflow should be collected.

The system should avoid collecting unnecessary:

* Personal information
* Identification information
* Financial information
* Health information
* Background information

unless a specific future feature requires it and appropriate governance has been established.

⸻

15. Document Storage

Credential documents should not simply be treated as ordinary database text.

A production system should use secure document storage with appropriate:

* Access controls
* Encryption
* Retention policies
* Deletion procedures
* Auditability

The database should store an appropriate document reference rather than unnecessarily duplicating document contents.

⸻

16. Privacy Principle

CredentialFlow should be designed with privacy and security from the beginning rather than adding them after development.

The system should support:

Collect only what is required.

Allow access only where authorised.

Record important actions.

Protect credential documents.

Retain information appropriately.

⸻

17. MVP Data Principle

The MVP should remain intentionally small.

The objective is not to collect as much information as possible.

The objective is to collect the right information to make the workflow work.

Less data. Clearer workflow. Better control.
